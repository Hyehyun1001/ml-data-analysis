# Mercari 분석 보고서 작성 규칙 (REPORT_GUIDE)

이 문서는 **보고서를 어떻게 쓸지 정의하는 규칙/spec 파일**이다. 실제 완성된 보고서가 아니다.

## 0. 최상위 원칙 — spec과 본문의 물리적 분리

- 이 파일(`REPORT_GUIDE.md`)과 실제 보고서(`report_초안_C.md` 및 그 PDF)는 **완전히 별개의 파일**이다.
- 이 파일의 어떤 텍스트도 `report_초안_C.md`/PDF 안에 등장해서는 안 된다. ("문서 형식", "서브 에이전트 전략" 같은 규칙 섹션 제목이나 내용이 보고서 목차·본문에 그대로 노출되는 것 금지)
- 보고서 산출물에는 **분석 내용만** 담는다. 이 문서를 어떻게 작성했는지에 대한 내부 작업 절차·에이전트 오케스트레이션·진행상황 체크표 같은 메타 정보는 절대 포함하지 않는다.
- **`report_초안_A.md`/`.pdf`, `report_초안_B.md`/`.pdf`는 동결(frozen)됨 — 절대 수정하지 않는다.** 현재 유일한 활성 작업 파일은 `report_초안_C.md`/`.pdf`뿐이다. 매 수정 라운드 후 `git diff --stat -- report_초안_A.md report_초안_A.pdf report_초안_B.md report_초안_B.pdf`로 무변경을 확인한다.

## 1. 보고서 구조 (Santander 보고서를 구조/디자인 reference로 재설계)

목차 순서와 각 장의 필수 내용은 다음과 같다. 데이터/수치/해석은 전부 Mercari 레포 실제 자료(`docs/pipelines/PIPELINE_base.md`, `teamipynb/`, `teamimage/`, `teamexcelsheet/`)에서만 가져온다 — 확인 안 되는 숫자는 추측해서 쓰지 않는다.

| 장 | 필수 내용 |
|---|---|
| 0. 초록 | 데이터 규모, 문제 정의(회귀·RMSLE), 참여 인원, 최고 성능 모델과 수치, 핵심 결론을 한 문단으로 |
| 1. 서론 | 문제 배경, 평가지표(RMSLE) 정의와 특성, 팀 진행 방식, 데이터 개요 |
| 2. 데이터 소개 | `describe`/`info` 기반 통계표, 컬럼별 자료형·결측 현황, 타깃 변수(`price`) 분포 |
| 3. 탐색적 데이터 분석(EDA) | 결측치 패턴, 카테고리 계층 구조, 브랜드·수치형 피처와 가격의 관계 — 표/그래프와 함께 |
| 4. 데이터 전처리 | 이상치 제거, 텍스트 정제, 결측치 처리 방식과 근거. **전/후 비교**(분포·성능 지표)를 반드시 근거로 제시 |
| 5. Feature Engineering | 벡터화/인코딩 방식(팀원별 비교), 파생 피처(길이·target encoding 등), vocab 크기 실험 |
| 6. 분석 방법 및 모델링 | 팀원별 사용 모델(Ridge/LightGBM/Lasso/FM_FTRL 등)과 선택 이유, 모델별 특성 해석(피처 중요도·회귀계수) |
| 7. 하이퍼파라미터 최적화 | 튜닝 대상 파라미터, 탐색 범위/방식, 결과값과 베스트 파라미터, 수동 튜닝과의 비교 |
| 8. 모델 성능 비교 및 분석 | **팀 전체 비교가 먼저, 개인별 서사는 9장으로.** 8.1 팀 전체 최종 성능 종합 비교(표+차트) / 8.2 최고 성능 모델 분석(원인 중심, 연대기 아님) / 8.3 모델 계열별(Ridge/Lasso/LightGBM/앙상블/블렌드) 교차 분석 / 8.4 최적화·Feature Engineering 효과(전/후/개선폭 표) / 8.5 팀 전체 공통 인사이트(팀원+수치+절번호 근거 필수) |
| 9. 팀원별 실험 상세 | 8장에서 다루지 않는 팀원별 고유 실험 서사(부속 자료 성격). 코드 블록·코드 스크린샷은 넣지 않고 핵심 접근법·주요 실험·RMSLE 결과·최종 기여만 담아 담백하게. 팀원당 시각화 자료 1개까지만(0개도 가능, 그 이상은 8장이나 5장으로), 분량(비공백 글자 수)은 팀원 간 ±50자 이내로 균등 |
| 10. 결론 및 회고 | 팀 전체 공통 결론은 8.5와 중복 없이 짧게 요약, 팀원별 회고(실명, teamexcelsheet 자료 기반) |

- 보고서는 **PDF**로 제작하며, 0장(초록) 바로 뒤에 장·subsection을 2단계까지 담은 **목차**를 둔다(2절 참고).
- 장·subsection 앞에 강제 페이지 나눔은 걸지 않는다. 남는 공간이 있으면 다음 장이 바로 이어진다(2절 참고).
- 팀원 공통으로 확인된 내용은 한 번만 종합하고, 팀원마다 고유하게 발견한 지점은 누가 무엇을 더했는지 밝히며 서술한다(예: "용우는 ~", "유경은 ~").
- **팀원 균형 원칙**: 특정 팀원의 성능이 가장 좋다는 사실은 축소하거나 숨기지 않되, 그 팀원의 실험 과정이 장 전체의 서술 분량을 지배하게 하지 않는다. 결과 장(8장)의 중심 주어는 "OO은"이 아니라 "팀 실험에서는", "모델별 비교 결과", "공통적으로 확인된 패턴은"이어야 한다. 개인별 상세 서사는 9장(팀원별 실험 상세)에 배치한다. 본문에서 5명을 나열할 때(예: "OO·OO·OO·OO·OO 5명이") 특정 팀원이 항상 첫 번째로 오지 않도록 나열 순서를 문단마다 바꾼다.
- **표 순서 원칙**: 팀원 이름이 행 또는 열로 들어가는 표는 두 유형으로 나눠 다르게 처리한다. (1) "팀원당 한 행/열" 비교표(예: 팀원별 사용 모델, 팀원별 alpha 튜닝 결과)는 표마다 팀원 순서를 의도적으로 다르게 섞어 특정인이 항상 먼저 나오지 않게 한다. (2) 담당자 열이 있는 실험 로그 표(예: 여러 팀원의 개선 단계를 모아놓은 표)처럼 한 사람이 여러 행을 차지할 수 있는 경우, 팀원 순서를 임의로 섞기보다 **하나의 명확한 수치 기준으로 전체를 정렬**(예: RMSLE 내림차순)하는 편이 더 가독성이 좋다 — 표 바로 위에 정렬 기준을 한 줄로 명시한다. 두 유형 모두 8.1 최종 성능 비교 표만은 예외로 RMSLE 오름차순(성능 좋은 순) 고정을 유지한다.
- 팀원 표기는 이니셜이 아닌 실명 사용 (HH→혜현, JH→진희, SH→소현, YG→유경, YW→용우).

## 2. Page-break / 레이아웃 규칙

- **목차·장·절 앞에 강제 page-break를 걸지 않는다.** 챕터(`##`)든 subsection(`###`)이든 목차든, 이전 내용이 끝난 자리에 남는 공간이 있으면 바로 이어서 시작한다. (구 버전은 모든 `##` 앞에 강제 개행을 걸어, 챕터가 페이지 초반에 끝나면 나머지가 통째로 백지가 되는 문제가 반복됐음 — 재발 금지. "각 장은 새 페이지에서 시작"이라는 과거 규칙은 폐기한다.)
- **표·그림·본문은 실제로 남은 공간에 들어가지 않을 때만** 다음 페이지로 넘어간다(`break-inside: avoid`를 표·그림에 적용해 내용이 중간에 잘리지 않게만 하고, 그 이상의 강제 개행은 걸지 않는다).
- **헤딩이 페이지 맨 하단에 제목만 홀로 남는 경우에만** 헤딩과 그 뒤에 이어지는 본문 도입부를 함께 다음 페이지로 넘긴다(헤딩에 `break-after: avoid`). 이건 헤딩 고아 방지용 최소 개입이며, 챕터 전체를 다음 페이지로 미는 강제 개행과는 다르다.
- 그림+캡션은 하나의 블록으로 묶어 캡션이 그림과 페이지 경계에서 분리되지 않게 한다.
- 위 규칙들의 결과로 불필요한 공백은 원천적으로 최소화된다 — 별도로 "장이 끝나면 여백 허용" 같은 예외를 두지 않는다.
- **목차는 1·2단계(장 + subsection, 예: `1`, `1.1`, `1.2`)까지 전부 표시**하되, 한 줄에 표시되는 글자 수를 줄이고 다단(예: 2열) 배치 등으로 간결하게 담는다.
- **본문 `p` 요소는 `text-align: left`를 쓴다. `justify`는 절대 쓰지 않는다.** 한글은 띄어쓰기 지점이 영어보다 적고 코드·영문 용어가 섞이면 더 줄어드는데, `justify`는 그 적은 space에 남는 폭을 몰아서 늘리기 때문에 짧은 줄(특히 볼드 소제목 문단)에서 단어 사이 공백이 비정상적으로 벌어지는 현상이 생긴다. 재발 방지를 위해 `report_style.css`의 `p` 규칙은 항상 `left`로 유지한다.

## 3. 자료 활용 원칙

- 각 ipynb의 마크다운 설명과 코드 주석을 확인하고, 다른 ipynb나 기존 자료에 이미 같은 내용이 서술되어 있는지 교차 검증한다.
- 다른 자료와 중복되는 내용이면 보고서에 반영하지 않고 무시한다.
- 중복되지 않는 고유한 내용이면 주석 원문을 그대로 옮기지 말고 보고서 문체로 재작성한다.
- 팀원별 시각화 자료(`teamimage/<이름>/`)가 있으면 반영하되, 흐름이 매끄럽지 않으면 넣지 않는다. 시각화가 없는 팀원은 본인 ipynb에서 중요한 차트를 추출해 동일 경로에 저장 후 반영한다.
- 특정 절에 쓸 만한 기존 이미지가 없다고 해서 다른 절에 이미 쓴 이미지를 그대로 재사용하지 않는다. 그 팀원의 노트북 셀 출력(예: epoch/round별 로그, print문 수치)에 실제 원본 데이터가 남아있다면, 그 데이터로 새 차트를 그려 저장한다(예: `teamimage/<이름>/0N_설명.png`) — 재사용보다 원본 데이터 기반 신규 시각화를 우선한다. 노트북에 그 절 내용을 뒷받침할 원본 수치가 전혀 없다면 이미지 없이 텍스트로만 서술하고, 지어내지 않는다.
- 전처리를 적용하기 전과 후를 비교해 실제 효과가 있었는지 분포·상관관계·모델 성능 지표 등 근거와 함께 제시한다.
- 전처리 방식은 두 유형으로 구분해 정리한다: **고정 적용형**(하나의 파이프라인을 정해 모든 모델에 동일 적용, 선택 근거 서술) vs **시도·비교형**(여러 기법을 순차 실험 후 최종 선택, 비교 결과를 표/문단으로 정리). 두 유형에 해당하는 노트북 목록과 각자 채택한 방법을 표로 요약한다.
- 모델링: 팀원별 사용 모델을 정리하고, 같은 모델 안에서 전처리·파라미터 변경에 따른 RMSLE 비교를 표로 만든다.
- 하이퍼파라미터 최적화 결과값과 베스트 파라미터를 기록해 수동 튜닝과의 차이를 비교할 수 있게 한다.

## 4. 표/Figure 규칙

- 표 헤더 행에는 옅은 배경색을 적용해 본문과 구분한다.
- 그림 바로 아래에 캡션을 붙인다(캡션이 그림과 분리되지 않도록 2절의 `break-inside: avoid` 준수).
- 추상적 서술 대신 표로 정리 가능한 비교(모델별 RMSLE, 파라미터별 결과 등)는 반드시 표로 제시한다.
- figure 크기는 페이지 폭을 넘지 않게, 텍스트와 그림 사이 여백을 과하지 않게 유지한다.

## 6. 최종 PDF 검수 체크리스트

PDF 생성 후 반드시 페이지 단위로 렌더링해 확인한다:

- [ ] 연속 2페이지 이상 이어지는 excessive blank space가 없는가
- [ ] 헤딩이 페이지 맨 아래에 단독으로 걸려있고 본문은 다음 페이지로 넘어가는 고아 현상이 없는가
- [ ] 그림/캡션이 페이지 경계에서 분리되지 않는가
- [ ] 표/그래프가 페이지 폭을 넘어 overflow되지 않는가
- [ ] 글씨 크기, 페이지별 정보 밀도가 전체적으로 균형 잡혀 있는가

## 7. 서브 에이전트 전략 (운영 규칙 — report_초안_C/PDF에는 노출되지 않음)

- 본 보고서는 실제로 서브에이전트를 스폰하여 작성한다 (총괄 에이전트 = 이 세션이 직접 오케스트레이션).
- 서브에이전트를 스폰해야 하는 상황이 발생하면, 스폰하기 전에 어떤 상황인지 먼저 사용자에게 보고한 뒤 진행한다.
- **총괄 에이전트**(이 세션): 각 에이전트에 작업을 지시하고, 결과가 정확한지 검토하며, 보고서가 1절의 장 순서대로 진행되는지 관리한다.
- **설명 에이전트**: 문단이 매끄럽게 이어지도록 초안을 작성하고, 작성 후 시각화가 필요한 부분을 차트 에이전트에게 넘긴다.
- **차트 에이전트**: 노트북 코드/출력 중 시각화할 수 있는 부분을 파악해 PNG로 저장하고(팀원 이름으로 구분), 어느 절에 쓰일 차트인지 파일명으로 표시한다.
- **검토 에이전트**: 문단과 차트가 매끄럽게 이어지는지, 이미지가 깨지지 않았는지 확인하고 필요하면 재작성을 요청한다.
